# Web Marketplace

`@token-streaming/web` is the Sites-hosted Web entry point and deployment composition root for the authorized-capacity marketplace. It provides a public sign-in entry, authenticated buyer/supplier workspaces, versioned JSON routes, D1 persistence, and server-only integration with the headless marketplace domain.

## Public technical-beta capabilities

- ChatGPT sign-in with server-derived tenant and actor identities.
- Individual and organization supplier registration.
- Encrypted supplier-gateway token submission and administrator authorization review. Suppliers can withdraw pending requests, revoke active authorizations, and replace a Gateway token after fresh live attestation; all three operations are tenant-scoped, command-bound, revision-CAS guarded, and never return token material. Revocation immediately scrubs credentials and heartbeats, blocks new work, drains unstarted reservations, and uses two-phase cancellation for leased artifacts. Token replacement fails and releases old-revision inference reservations that have not entered `running`, records `GATEWAY_CREDENTIAL_ROTATED`, preserves already-running work, and clears the old Agent heartbeat. Capacity-offer publication is a single `INSERT ... SELECT` guarded by the exact live authorization revision, credential generation, validity, and supplier version. Credential AES keys and the now-independent Agent lookup HMAC use bounded active/previous keyrings with explicit persisted key ids, legacy dual-read, signed-request lazy lookup migration, bounded CAS rewrap, persistent key canaries, and retirement backlogs. Approvals are command-guarded, an administrator cannot review their own tenant, expired credentials fail closed, and rejected credentials are scrubbed. Evidence references accept identifiers only and reject common API-key, token, JWT, and unprefixed high-entropy credential shapes before they can enter append-only events.
- Event-sourced supplier activation and capacity-offer publication through `@token-streaming/marketplace-domain`.
- Durable offers, inference jobs, schema-versioned marketplace events, usage records, audit events, idempotency records, and append-only ledger entries in D1.
- Immutable per-job service evidence that snapshots the purchased Provider/model, actual served model, quoted unit price, measured usage, final charge, provider request ID, and evidence digest.
- Fail-closed P0/P1 matching with capacity, concurrency, validity, balance, and gateway-host controls. Synchronous and artifact work share one atomic reservation budget; settlement is conditional on a live reservation and cannot exceed its ceiling.
- Input minimization: prompt bodies are not persisted. New content digests are converted to tenant/resource-bound HMAC commitments before persistence, so low-entropy prompts cannot be tested with an offline SHA-256 dictionary. Outputs use a separate AES-256-GCM content key and bounded replay window.
- Explicit privacy intent: `strict` is the UI default, supplier/upstream plaintext visibility requires affirmative acknowledgement, and buyers can actively purge ordinary outputs, files, or file tasks without rewriting append-only financial evidence.
- Buyer-only content views prevent suppliers from reading customer filenames and replayable outputs through the dashboard. Login email/name remain in the identity service instead of being duplicated in market D1.
- Durable D1 rate limits cover authenticated mutations and signed Agent calls; browser writes require same-origin checks and security headers deny caching, framing, referrers, MIME sniffing, and unnecessary device capabilities.
- The automated D1 migration-integrity test applies the authoritative 0000–0015 chain to a temporary local database, seeds legacy inference and artifact rows after 0000–0003 plus pre-keyring authorization rows before 0011, and verifies all 24 tables, authorization lifecycle/revision columns, keyring lifecycle tables, one-way fresh-bootstrap provenance, legacy-data transitions, privacy defaults, crypto format/key ids, persistent key canaries, reservation/cancellation/upload-state/deadline columns, the independent object-deletion tombstone, and financial/security indexes. Runtime bootstrap independently checks every additive column, transactionally upgrades the legacy authorization-status CHECK, installs global lifecycle-command uniqueness, and safely rechecks after a concurrent Worker-isolate migration race.
- Installable consumer PWA metadata and a minimal service worker that never caches authenticated pages or API responses.
- Supplier onboarding guidance for the separate cross-platform Supplier Agent; Provider credentials remain on the supplier device.
- Resumable browser uploads up to 256 MiB in fixed 4 MiB chunks, for at most 64 immutable generations. Each chunk is hashed client-side, authenticated with tenant ownership, encrypted with AES-256-GCM, and stored under an immutable R2 key. A D1 `pending → ready` handoff prevents concurrent writers from mismatching metadata and bytes. Before purge attempts R2 deletion, one D1 batch both enqueues each object's durable `artifact_object_deletions` retry and changes the exact immutable generation identified by artifact, tenant, part number, storage key, and upload time from `pending`/`ready` to `deleting`. The queue therefore cannot remain permanently filtered by a stale `ready` generation. Purge advances at most four generations for one artifact per invocation; an explicit buyer purge that has more generations remaining, or whose R2 delete fails, returns retryable HTTP 503 and can be invoked again. A 64-generation file therefore needs at most 16 successful bounded invocations. The artifact is marked `deleted` only after every generation metadata row is gone. Its full-purge audit is an idempotent completion effect: both the transition path and any later explicit retry insert a missing event using the stable action/resource audit ID, while tenant/action/resource lookup prevents duplicates. The independent tombstone survives chunk metadata for 24 hours and repeats the idempotent R2 delete every 10 minutes.
- Asynchronous artifact scheduling uses short-lived Supplier Agent capability heartbeats, exact offer/authorization/model/media matching, 5-minute leases, at most three attempts, encrypted instructions, atomic monotonic checkpoints, a 30-minute queue timeout, and a 6-hour absolute execution deadline per claimed attempt. Lease renewal is capped by that deadline and completion checks the database clock plus the exact final checkpoint. Buyers can idempotently cancel queued work immediately; the command ID is first bound to exactly one task. Leased work enters `cancelling`, retains its financial reservation, and becomes terminal when the lease holder observes cancellation, the lease expires, or the absolute deadline arrives.
- Standard artifact input expires after 48 hours and results after 24 hours. Strict uploads hide the original filename, use a 60-minute waiting/result window, and schedule input deletion at terminal state. `artifact_tasks.content_purged_at` is also set when an expired result is erased, so that column alone is not proof of full task-content purge. Full purge requires the task marker to be present, the instruction fields to be empty, all output ciphertext/IV/expiry fields to be empty, the associated artifact to be `deleted` with a purge time, and no chunk generation to remain. The task purge endpoint therefore remains available after the standard 24-hour output expiry so the associated 48-hour input can still be actively cleared. Once those full conditions hold, a later explicit task-purge retry idempotently backfills both missing artifact- and task-level completion audits without duplicating either event. An independently bearer-authenticated, pre-auth rate-limited sweep is requested every 10 minutes and traffic also triggers bounded cleanup; expired R2 bytes, chunk metadata, raw manifests, instructions, credentials, nonces, heartbeats, and result ciphertext are removed while keyed commitments, audit, evidence, and financial history remain. Before mutating retention state, maintenance requires all four production key domains to be present, valid base64 decoding to exactly 32 bytes, and pairwise distinct; invalid configuration fails the request. Cleanup transitions remain small and resumable: each invocation advances at most four due deletion-queue keys, one expired artifact, and four immutable generations for that artifact. Complete maintenance also runs schema bootstrap and is not compatible with the lower D1 per-invocation query ceiling; production requires the Workers Paid 1,000-query quota. Maintenance reports object-deletion backlog/overdue/oldest-due/24-hour breach state, `unclaimedExpiredArtifacts` with its oldest expiry and 24-hour breach count, and `pendingArtifactTombstones` with its oldest purge start and 24-hour breach count. Scheduled monitoring requires an exact HTTP 200 success envelope, rejects any of the three retention-breach counts, and also thresholds the overdue deletion, unclaimed artifact, and pending generation backlogs. Scheduler delivery can be delayed and is not a hard deletion SLA.

The browser never receives provider credentials and cannot choose another tenant. Provider-specific wire formats stop at the server-side gateway adapter. Local Codex is used only for engineering and is never a customer inference route.

The browser/control-plane artifact contract remains `gongsuanyun.artifact.v1`. Its additive `cancelling` value means “non-terminal and reservation still held”; v1 consumers must continue polling and treat future unknown non-terminal task states conservatively instead of mapping them to `cancelled`. Clients with an exhaustive legacy status enum must upgrade. The Supplier Agent wire contract is separately versioned as `gongsuanyun.artifact-worker.v2`; v1 workers are rejected rather than silently downgraded.

## Authorized supplier-node contract

An approved HTTPS supplier node receives signed `gongsuanyun.gateway.v3` JSON with `model`, `input`, `data_class`, `max_output_tokens`, and `stream: false`. Every request includes a timestamp, one-time nonce, job ID, and HMAC-SHA256 signature over the exact body digest. Before approval, the control plane sends a signed one-time challenge to `/v3/attestation` and requires the live Provider identity, exact model inventory, P0/P1 scope, and capacity to contain the requested authorization. It returns normalized output and a signed execution-evidence envelope:

```json
{
  "output": "...",
  "usage": {
    "input_tokens": 120,
    "output_tokens": 80,
    "total_tokens": 200
  },
  "execution_evidence": {
    "evidence_version": "gongsuanyun.execution-evidence.v1",
    "request_id": "job-...",
    "provider_id": "authorized-provider",
    "requested_model": "exact-model-id",
    "served_model": "exact-model-id",
    "provider_request_id": "provider-request-...",
    "input_sha256": "64 lowercase hex characters",
    "output_sha256": "64 lowercase hex characters",
    "usage": {
      "input_tokens": 120,
      "output_tokens": 80,
      "total_tokens": 200
    },
    "completed_at": "2026-08-25T00:00:00.000Z"
  },
  "execution_evidence_signature": "HMAC-SHA256 lowercase hex"
}
```

The control plane checks the exact Provider and model, input/output digests, usage, completion window, and HMAC signature before calculating settlement. The verified evidence row, usage record, buyer debit, supplier credit, platform fee, and completed job update are committed as one D1 batch. Any missing, malformed, substituted, or tampered evidence returns `SERVICE_EVIDENCE_FAILED`; the job fails and no financial entries are created.

Production approval requires the gateway hostname in `MARKETPLACE_GATEWAY_HOST_ALLOWLIST` and a successful live attestation. Gateway requests reject redirects so an allowlisted public URL cannot bounce into a private network. The platform requires separate 32-byte base64 credential, content, artifact, and commitment secrets, all managed by Sites runtime configuration rather than source files. Gateway credentials can additionally use `MARKETPLACE_CREDENTIAL_KEYRING` and the independent `MARKETPLACE_CREDENTIAL_LOOKUP_KEYRING`, each encoded as `{"active":"key-id","keys":{"key-id":"base64-32-byte-key"}}`; the legacy `MARKETPLACE_CREDENTIAL_KEY` and `MARKETPLACE_COMMITMENT_KEY` remain dual-read aliases during rollout. Ring size is capped at eight, ids are persisted separately from format versions, and maintenance refuses missing referenced ids or a key that no longer matches its persistent canary. Before removing the legacy credential key, both `credentialEncryptionRotationBacklog` and `legacyCredentialContentReferences` must be zero because format-v1 replayable inference/artifact content also used that key. After the lookup backlog reaches zero, a successful recovery check has completed, and the new ring remains configured, operators may set `MARKETPLACE_CREDENTIAL_LOOKUP_LEGACY_ENABLED=false`; maintenance then proves that no persisted lookup still requires the old commitment material while `MARKETPLACE_COMMITMENT_KEY` remains available for long-term evidence verification. Any other flag value fails closed. One gateway token may expose at most 100 simultaneous valid authorizations to an Agent; approval of the 101st is atomically refused before it can disable existing permissions, while an already-invalid over-limit signed request fails explicitly and drains its verified old lookup namespaces instead of silently omitting permissions. The maintenance endpoint additionally requires `MARKETPLACE_MAINTENANCE_KEY`, compares its bearer credential through fixed-length digests, is independently rate-limited before authentication, and is never authorized by browser identity headers.

Sites does not return secret values in plaintext, so ADR 0009 adds eight independent write-only slots per Gateway key domain plus a strict non-secret manifest. Slot material is bound to domain and key id by an HMAC verifier; staged keys cannot enter encryption, decryption, lookup, or nonce namespaces. D1 persists the applied manifest generation/canonical hash and append-only key lifecycle events, so a lower generation, same-generation substitution, or later manifest removal fails closed. Lifecycle command IDs are globally unique across both key domains and every apply/register/baseline action. `POST /api/internal/cryptography/preflight` is D1-read-only, treats pre-upgrade lifecycle tables as unavailable rather than creating them, and remains diagnosable when the lookup ring is broken; `manifest/apply` and `keys/register` are separate maintenance-authenticated lifecycle writes. Ordinary maintenance never creates a missing canary. A separate `keys/baseline` action can establish a configured readable-key canary only while a migration/runtime-bootstrap-created fresh-database eligibility row remains unconsumed, complete durable business history is still empty, and an independently recorded material verifier matches. The canary, append-only event, and one-way eligibility consumption are one D1 batch, so the action supports a compatibility or slot-only fresh installation but cannot repair a restored or already-used database. These controls do not reconstruct a key or replace independent KMS/HSM custody. Live D1 references reaching zero permits only runtime retirement, not immediate deletion of the Sites copy or destruction of the final recovery copy, because retained backups may still contain old ciphertext or lookup digests. Follow the [Gateway key disaster-recovery, re-rotation, and rollback runbook](../../docs/runbooks/gateway-key-disaster-recovery-and-rotation.zh.md) and [ADR 0009](../../docs/adr/0009-gateway-key-custody-slot-manifest-and-recovery.zh.md).

Local `.env`/`.env.*`, `.dev.vars`/`.dev.vars.*`, and `.wrangler/` files are ignored by the repository, except that `.env.example` templates remain tracked. Ignore rules are not a secret manager: production values belong in Sites runtime configuration and local secret files must not be copied into commits, logs, or build artifacts.

## Production launch prerequisites

- Run the Web deployment on Cloudflare Workers Paid with the 1,000 D1 queries-per-invocation quota. This is a hard prerequisite for the full maintenance endpoint, including `ensureSchema()` bootstrap; the four-generation cleanup batch size is a resumability and blast-radius bound, not compatibility with a lower query ceiling.
- Configure and monitor the authenticated 10-minute maintenance workflow. Treat a non-200 response, any 24-hour retention breach, or a thresholded deletion/unclaimed/tombstone backlog as a release-blocking operational fault.
- Apply D1 migrations through 0015 before enabling lifecycle routes. Verify that pending withdrawal and active revocation work on any database previously created by runtime bootstrap; the startup compatibility upgrade must replace the legacy three-state status CHECK, install global lifecycle-command uniqueness, and leave fresh-bootstrap eligibility absent on a database with durable history.
- Provision all distinct 32-byte cryptographic domains and the maintenance bearer secret through runtime configuration, never through tracked or build-output files. On a truly fresh database only, establish each configured readable-key baseline from an independently stored verifier before accepting any reference. Introduce credential/lookup slots using staged manifest → read-only preflight → explicit manifest apply → canary registration → readable warm-up → active switch → CAS/lazy migration → zero-reference retirement; never overwrite a legacy secret in place.
- Keep an independently recoverable, tested copy of every readable key and execute the key-custody runbook before rotation or retirement. Treat runtime retirement, Sites-secret deletion, and destruction of the final recovery copy as three separate approvals.
- Once format-3 credential or lookup rows exist in live D1 or a retained backup, deploy only readers that support v1/v2/v3 plus persisted key ids. A failure requiring an older incompatible release must be fixed by rolling forward.

Artifact storage additionally requires a separate 32-byte base64 `MARKETPLACE_ARTIFACT_KEY` and the `ARTIFACTS` R2 binding. The key is never returned to the browser or Supplier Agent. AES-GCM additional authenticated data binds tenant, artifact, part number, and plaintext digest, and both ciphertext and plaintext digests are checked on every supplier download.

Encryption at rest is not execution secrecy: the matched Supplier Agent and its upstream Provider receive plaintext while running a task. Customers requiring execution-party confidentiality must use a customer-controlled node or a future remotely attested confidential-computing tier.

The current balance is a public technical-beta promotional balance. Cash collection, tax invoicing, KYC/KYB evidence storage, and payouts require external regulated providers before public commercial launch.

The `node-signed-provider-response` assurance level proves that the hardened supplier-node observed and signed the upstream response model; it is not independent cryptographic proof from the upstream Provider. Stronger future tiers require official provider-signed receipts, platform-managed provider accounts, or attested confidential-computing workers.
