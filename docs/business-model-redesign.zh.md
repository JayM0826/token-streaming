# 共算云商业模式重构与验证路线图

- 状态：Business owner review
- 基准日期：2026-08-26
- 适用范围：当前仓库中的授权推理容量市场、Web Marketplace、Supplier Node 与 Supplier Agent
- 事实口径：仓库实现、官方供应商条款/价格/地区文档和中国监管原文
- 不构成：法律、税务、支付、证券或会计意见

## 0. 决策摘要

建议保留“经授权、可计量、可审计的推理容量交易”技术内核，但重构首发商业模式：

> 从“个人把剩余订阅/API 额度拿出来共享”转为“面向企业异步工作负载的授权容量采购、智能路由与推理 FinOps 平台”，先做受管市场，再验证是否具备开放市场的流动性。

首发不应是消费级聊天产品，也不应把个人订阅作为主要供给。首发应只服务一个地区、一个工作负载族和少量设计伙伴，以平台自有授权项目、签约推理服务商或可证明商业授权的自托管模型作为供给。

商业上的核心改变有六项：

1. 交易资产从“账号/额度”改为“带授权、地区、模型、性能和成本边界的推理服务承诺”。
2. 主力需求从泛消费者改为 P0/P1、可延迟、可批处理的 B2B 工作负载。
3. 主力供给从个人订阅改为平台授权容量、签约推理端点、自托管商业模型和企业专属项目。
4. 收费从固定抽取总流水改为“透明平台费 + 节省分享 + 企业控制面订阅”，供应方报价表示净应付。
5. 产品从“最低价 API”升级为“成本、可靠性、数据策略和结算证据的统一控制面”。
6. 在取得书面供应授权、地区结论、真实成本和付费需求前，暂停公开市场、现金余额、个人出款和 P2/P3。

## 1. 从头还原当前商业模式

### 1.1 当前参与者

| 参与者 | 当前设定 | 实际责任 |
| --- | --- | --- |
| 购买方 | 个人、团队、企业 | 提交推理任务，确认明文会被供应节点与上游处理，按实际用量付费 |
| 供应方 | 个人或企业 | 提供经授权的 Provider 项目、订阅连接器或自托管端点，声明容量与报价 |
| 平台 | 共算云 | 准入、报价展示、撮合、任务路由、用量验证、账本、风控、争议处理 |
| 上游 Provider | 模型/API 服务商 | 实际执行推理并施加地区、授权、数据与计费规则 |
| 支付/KYC 服务商 | 尚未接入 | 真实收款、身份核验、分账、税务信息和供应方出款 |

### 1.2 当前交易链

    供应方注册
      -> KYC/KYB 与授权审核
      -> Supplier Node/Agent 在线证明
      -> 发布 CapacityOffer
      -> 购买方选择模型和数据等级
      -> 平台按价格选择报价并预留余额/并发
      -> 供应节点调用上游 Provider
      -> 节点签署执行证据
      -> 平台核验用量、扣买方余额、记供应方收入和平台费

技术链路已经覆盖了闭测所需的大部分安全与审计骨架，但真实资金、真实身份、税务、发票、出款和供应商合同仍未闭环。

### 1.3 当前收入和成本设定

- Web 运行时默认按买方结算金额的 12% 记平台费。
- 供应方收到买方结算金额减平台费后的余额。
- 文档另有一套“供应方成本 + 支付 + 风险 + 目标毛利”的买方加价公式。
- 会员方案覆盖并发、预算、审计、RBAC 和 SLA，推理继续按量收费。
- 购买方目标价格被设定为至少比可比官方路径低 10%。

这四个设定目前没有形成同一套可执行价格语义。

## 2. 必须先证伪的原始假设

### 2.1 “个人剩余额度”通常不是经济意义上的闲置算力

按量 API 项目没有被闲置的固定资产：多处理一百万 token 就多产生一笔上游成本。它只有配额，没有天然成本折扣。个人订阅与 API 还是不同产品、不同账单；以 OpenAI 为例，ChatGPT 与 API 分开计费，API 仍按 token 收费。

更重要的是，公开条款通常不支持把账号、Key 或服务额度当作可流通资产：

- OpenAI Services Agreement 允许客户把 API 集成进自己的 Customer Application，但禁止转售/出租账号访问，也禁止买卖或转移 API Key。
- OpenAI Service Credit Terms 明确服务额度不可转移、出售或兑换现金。
- Google Cloud Credits 也明确不可出售、不可转移，只能用于客户自己的账号。

因此，“个人订阅容量”即使保留在领域类型中，也必须默认关闭。只有供应商针对该连接器给出书面许可、正式授权和可验证计量后才能逐项开启。

真正可能有折价空间的供给只有：

1. 平台或合作方取得的合同折扣、批量折扣或官方分销权限。
2. 已预购 Reserved/Provisioned Throughput 且合同允许服务终端用户的未利用容量。
3. 自托管开源模型的闲置 GPU 时间，且模型许可证、数据和地区均允许商用。
4. 专业推理服务商愿意以批发价换取平台需求和更高利用率。

### 2.2 官方低价通道会直接压缩平台价差

OpenAI Batch、Anthropic Message Batches、Gemini Batch 目前均公开提供约 50% 的异步价格折扣；OpenAI、Gemini 等还提供 Flex/Reserved/Provisioned 等不同成本与 SLA 档位。

这意味着“把同步 API 便宜一点”不是稳定壁垒。首发必须同时做到：

- 比客户自己使用官方 Batch/Flex 更省操作和治理成本；
- 跨供应方统一预算、证据、隐私和失败语义；
- 在官方单一渠道不可用或不适合时提供有边界的替代；
- 对批量任务提供拆分、恢复、验证和成本上限，而不仅是转发。

### 2.3 最低价路由不是充分价值

OpenRouter 已提供统一 API、数百模型、多供应商、价格/吞吐/延迟路由、ZDR 过滤、BYOK 和企业控制，并以约 5.5% 的充值平台费作为公开基准。其供应方也是可运营的推理端点，而不是普通消费者账号。

因此共算云不能只以“更多供应商、自动找低价”定位。可差异化的能力应是：

- 授权与执行证据进入同一结算链；
- 可验证的供应节点与文件异步任务；
- 供应方准入、应付、准备金和争议处理；
- 面向特定地区/行业的数据策略；
- 企业成本中心、审计和专属供应池；
- 对异步任务的最高费用预留、断点恢复和失败不扣款。

### 2.4 大众消费者不是合适的首发客户

消费用户单客支出低、支付和客服占比高、退款/欺诈更频繁，还会引入应用商店、内容安全和未成年人义务。当前产品最强的能力——授权证据、账本、数据等级、文件任务和供应节点——对企业更有价值。

建议首发只做 B2B API 与管理控制台。消费聊天、原生移动端和应用内购买在单位经济得到证明后再评估。

## 3. 优化后的战略定位

### 3.1 一句话定位

共算云是一个“合规的多模型容量采购、异步执行与推理 FinOps 控制面”：企业提交有预算和数据边界的任务，平台从经授权的供应池选择可验证的执行路径，并按真实用量和服务证据结算。

### 3.2 客户真正购买的不是 token

客户购买的是一个版本化服务承诺：

    Provider / 精确模型 / 模型版本
    + 输入、缓存、输出及工具费率
    + 地区与数据处理策略
    + 最大费用和完成窗口
    + 性能与可用性目标
    + 失败、重试、退款语义
    + 执行证据与争议窗口

token 只是计量单位之一。

### 3.3 首发楔子

首发 ICP：

- 有稳定批量推理需求的 AI 原生中小团队或软件公司；
- 任务可以延迟几分钟到 24 小时；
- 数据等级为 P0/P1；
- 任务可独立重放和验证；
- 客户愿意通过 OpenAI-compatible API 或文件任务接入。

优先工作负载：

- 文本分类、抽取、清洗、翻译、摘要；
- RAG 预处理、离线评测和合成测试数据；
- 商品/内容元数据生成；
- 大批量结构化转换；
- 非实时 Agent 的离线步骤。

暂不服务：

- 医疗、金融决策、法律意见等高风险结果；
- P2/P3、国家秘密、重要数据或默认出境数据；
- 低延迟强 SLA 的实时对话；
- 工具执行、代码沙箱、浏览器自动化；
- 面向公众的无限聊天套餐。

## 4. 供给侧重构

### 4.1 供应分层

| 层级 | 供给类型 | 首发 | 说明 |
| --- | --- | ---: | --- |
| S0 | 平台自有、合同明确的 Provider 项目 | 必须 | 建立单供应源闭环和成本基准 |
| S1 | 签约推理服务商、官方分销商、托管开源模型端点 | 必须争取 | 真正形成批发价和多供应源 |
| S2 | 企业 BYOC/BYOK 专属项目 | 可做 | 主要卖控制面，不混入公共池 |
| S3 | 经 KYC 的个人/小团队自托管 GPU 端点 | 后续试点 | 仅 P0，性能、许可、运维和明文风险都需更严格 |
| S4 | 个人 API PAYG 项目 | 默认关闭 | 没有天然闲置成本，需 Provider 书面许可和真实折扣 |
| 禁止 | 消费订阅、共享 Key、Cookie、账号、积分倒卖 | 永久禁止 | 无授权、不可计量或不可转让 |

### 4.2 供应方资格

每个可售报价必须同时满足：

- 供应主体与受益所有人已核验；
- 上游合同明确允许该应用、终端用户地区和商业模式；
- Provider、模型、版本、地区、数据等级、有效期均明确；
- 输入、缓存、输出、工具、媒体等原始计费单位可验证；
- 具有 Provider 请求 ID、上游账单或更强回执；
- 节点达到对应可信等级；
- 供应方接受数据处理、事故通知、争议和删除义务；
- 供应方净报价在经济阈值内。

节点自签证据只能证明官方节点观测到了某个响应，不能证明上游 Provider 本身不可抵赖。产品文案、保障等级和赔付规则必须反映这一点。

## 5. 产品与价格分层

### 5.1 三个 SKU

| SKU | 客户价值 | 路由 | 价格策略 | 首发 |
| --- | --- | --- | --- | ---: |
| Spot Batch | 最低成本、有完成窗口 | Batch/Flex/闲置自托管容量 | 保证相对可比路径节省 | 是 |
| Managed Realtime | 统一 API、故障切换、预算治理 | 标准/优先供应池 | 供应成本 + 透明平台费 | 小范围 |
| Private Pool | 数据策略、专属容量、审计与 SLA | 客户 BYOC 或专属签约池 | 月费/承诺 + 成本转嫁 | 后续企业 |

不同 SKU 解决不同问题。只有 Spot Batch 承诺“低于可比官方路径”；Managed Realtime 和 Private Pool 的价值是可靠性、治理与合规，可以在透明前提下与官方价持平或更高。

### 5.2 报价语义

必须区分四个金额：

- S：供应方净报价，即完成任务后供应方应得的未税金额。
- O：支付、汇率、风险、网关、存储和支持等可归属变量成本。
- F：平台服务费。
- B：买方税前价格，B = S + O + F。

供应方报价不再表示买方价格，也不再在成交后被平台费二次扣减。税务代扣、确认的拒付和供应方 payout 费用应单列，不能混入平台抽成。

### 5.3 Spot Batch 的节省分享

设 R 为同 Provider、同模型、同档位、同地区和同数据策略的可比参考价；g 为买方最低节省率；α 为平台分享的可实现节省比例。

    可实现节省 Δ = R - S - O
    平台服务费 F = max(最低服务费, α × Δ)
    买方价格 B = S + O + F
    发布条件：
      B <= R × (1 - g)
      且 F 能覆盖平台最低贡献要求

建议试验起点，不是公开承诺：

- g：10% 至 15%
- α：20% 至 30%
- 最低服务费：按任务或月度承诺设置，避免极小请求亏损

例：把可比价 R 归一化为 100，供应方净报价 S 为 60，变量成本 O 为 5，α 为 25%，则 F 为 8.75，买方价格 B 为 73.75。买方节省 26.25，供应方获得 60，平台以 8.75 覆盖控制面和利润。

这个公式让平台、买方和供应方共同受益于真实折扣；如果没有真实折扣，就不把报价包装成“共享省钱”。

### 5.4 Managed 与 Private 的收费

建议只保留一项透明平台收费，避免同时向买卖两侧隐形抽成：

| 套餐 | 建议验证方式 | 收费逻辑 |
| --- | --- | --- |
| 开发者试用 | 邀请制、限额 | 小额按量服务费，不承诺 SLA |
| 团队 | 月度平台费 + 较低用量费 | 预算、审计、成本中心、API Key 管理 |
| 企业 | 年度最低承诺 | SSO、合同 SLA、数据地区、专属供应池、支持 |

具体人民币或美元标价要等地区、PSP、税费、供应合同和 10 个以上付费访谈后再定。现有 ¥29/¥99 等消费型套餐不应作为首发锚点。

## 6. 单位经济与报价闸门

### 6.1 贡献利润

每笔任务的贡献利润：

    CM = B
       - S
       - 支付费
       - 汇率损益
       - 退款/拒付准备
       - 网关、存储和网络成本
       - 内容安全与支持的可归属成本

    CM% = CM / B

会员费、营销赠送和尚未发生的规模效应不能用于掩盖负的任务贡献利润。

### 6.2 必须按原始计费单位结算

当前实现只用 total_tokens × 单一每百万 token 价格结算，而主要 Provider 的输入、缓存、输出和长上下文费率显著不同。单一总 token 价格会导致：

- 输出占比高的任务可能让供应方亏损；
- 输入占比高的任务可能让买方被过度收费；
- 供应方会选择性接收对自己有利的任务，形成逆向选择；
- 无法正确比较 Batch、Flex、缓存和长上下文路径。

现金交易前必须把报价与结算改为不可变 RateCard：

    input_rate
    cached_input_rate
    cache_write_rate
    output_rate
    long_context_band
    tool/media/compute rates
    region/service-tier uplift

每项用量分别乘以对应费率，再计算平台费、税和准备金。

### 6.3 现金上线前的经济闸门

一个组合只有同时满足以下条件才可售：

- 取得可核验的供应成本；
- 价格单位覆盖该 Provider 的所有计费维度；
- p90 任务贡献利润为正；
- p50 Spot 报价达到承诺节省率；
- 上游账单与平台计量差异低于合同阈值；
- 退款、失败和部分完成已计入压力测试；
- 供应方应付不依赖未来新增买方资金。

## 7. 商业模式画布

| 模块 | 优化后选择 |
| --- | --- |
| 客户细分 | 有稳定 P0/P1 批量推理的 AI 团队；需要统一治理的 SaaS 企业；后续专属供应池客户 |
| 价值主张 | 更低的异步 landed cost；统一 API；预算上限；可验证执行与结算；数据策略；供应故障隔离 |
| 渠道 | 创始人直销、技术社区、API 迁移合作、推理服务商联合销售 |
| 客户关系 | 设计伙伴、集成支持、用量复盘、企业 SLA；暂不做大规模消费者客服 |
| 收入 | 节省分享、透明路由服务费、团队/企业控制面订阅、专属池与 SLA |
| 核心资源 | 供应合同、需求聚合、路由与价格数据、证据账本、供应节点、合规与风控能力 |
| 核心活动 | 采购/准入、能力探测、报价、调度、计量对账、争议、企业 FinOps |
| 合作伙伴 | 授权 Provider、推理服务商、自托管模型运营商、PSP、KYC/KYB、税务与法务 |
| 成本结构 | 供应结算、支付/汇率、基础设施、支持、风控、合规、销售、准备金 |

## 8. 增长飞轮与护城河

### 8.1 可成立的飞轮

    更多合格批量需求
      -> 更好的采购条款和供应利用率
      -> 更低 landed cost
      -> 更高报价接受率
      -> 更多真实性能/成本数据
      -> 更优路由和更低失败成本
      -> 更多合格需求

另一个企业飞轮：

    统一账单与策略
      -> 更多工作负载接入
      -> 更完整的成本与可靠性画像
      -> 更好的治理和供应谈判
      -> 更高切换成本与续约率

### 8.2 不是护城河的能力

- OpenAI-compatible API 本身；
- 模型列表；
- 简单最低价排序；
- 前端聊天界面；
- 宣称“个人共享更便宜”；
- 节点自签但无法对账的用量。

真正的壁垒是授权供给、需求密度、真实路由数据、证据结算、企业工作流和地区合规组合。

## 9. 地区与合规策略

### 9.1 不把中国大陆与国际市场混成一个发布面

OpenAI 和 Anthropic 当前公开支持地区列表均不包含中国大陆；Google AI Studio/Gemini API 也按可用地区限制访问。任何境外 Provider 都必须同时满足签约主体、最终用户和流量来源地区要求，不能通过代理绕过。

若面向中国大陆公众提供服务，《生成式人工智能服务管理暂行办法》把 API 方式提供生成内容也纳入“服务提供者”定义；具有舆论属性或社会动员能力的服务涉及安全评估和算法备案。2025-09-01 起，生成合成内容标识还要求显式/隐式标识及相关用户协议、传播和日志能力。境内数据发给境外模型还需逐场景评估数据出境路径。

因此建议维护两条完全独立的商业走廊：

| 走廊 | 供给 | 客户 | 货币/支付 | 发布条件 |
| --- | --- | --- | --- | --- |
| 国际支持地区 | 当地可用的授权 Provider/推理端点 | 当地企业 | 当地支持的币种与 PSP | 当地实体、合同、税务和数据结论 |
| 中国大陆 | 已完成本地可用性与备案/登记评审的国内 Provider 或自托管模型 | 境内企业/公众分别评估 | CNY 与持牌支付 | AI 服务、标识、数据、ICP/电信、支付和税务结论 |

当前协议硬编码 CNY，而境外供应商又可能是主要首发供给，这一矛盾必须由首发地区决策解决，不能靠汇率字段临时掩盖。

## 10. 当前产品与新商业模式的差距

| 差距 | 当前证据 | 商业影响 | 优先级 |
| --- | --- | --- | ---: |
| 单一 total token 单价 | packages/marketplace-domain/src/settlement.ts | 无法覆盖输入/输出/缓存差价，可能倒挂 | P0 |
| 平台费从供应报价中扣除 | 同上，默认 1200 bps | 与文档“供应方净报价”冲突 | P0 |
| 只按最低价格选 offer | apps/web/server/marketplace-service.ts | 没有地区、可靠性、集中度和隐私评分 | P0 |
| RunInferenceRequest 无地区/Provider 约束 | packages/protocol/src/marketplace-api.ts | 买方无法锁定地区与数据路径 | P0 |
| 个人 subscription-plan 是正常成功路径 | marketplace-domain 测试与协议 | 容易被误解为可直接商用 | P0 |
| 只有推广余额 | apps/web/README.md | 未接真实收款、KYC、税务、发票、出款 | P0 |
| 节点签名不是上游证明 | apps/web/README.md | 欺诈与争议仍需账单对账和准备金 | P0 |
| CNY 单币种 | marketplace API | 与国际首发/供应方结算不兼容 | P1 |
| 消费 UI 与多端计划过早 | 现有产品路线 | 分散验证商业模式的资源 | P1 |

建议立即做的产品调整：

1. 用 feature flag 默认关闭 subscription-plan 与普通个人 API 项目。
2. 在协议中区分 supplier_net_ask、buyer_quote、platform_fee、external_costs、tax。
3. 将统一单价升级为版本化多维 RateCard。
4. 报价中加入 reference price、节省率、数据地区、保留策略、完成窗口和保障等级。
5. 调度器先做硬约束，再按 landed cost、可靠性、延迟和集中度评分。
6. 将 Spot Batch 设为默认试点入口；实时与文件任务使用不同 SLA/价格卡。
7. 真实资金上线前接入持牌 PSP、KYC/KYB、税务/发票和出款对账。

建议暂停：

- 公开个人供应招募；
- 消费级会员和无限聊天；
- 原生移动端；
- P2/P3 与“端到端加密”营销；
- 未书面授权的境外 Provider；
- 任何可提现平台余额。

## 11. 90 天验证路线图

### 阶段 A：第 0–14 天，问题与需求验证

动作：

- 访谈至少 15 个目标买方，按批量任务、月用量、延迟、数据等级、现有 Provider 和采购障碍记录。
- 获得至少 3 份包含具体工作负载、预计用量和可接受价格的设计伙伴意向。
- 访谈至少 8 个潜在供给方，只记录能提供书面商业授权和成本证据的供给。
- 选择一个首发地区、签约主体、结算币种和一个工作负载族。

退出条件：

- 至少 3 个客户愿意提供真实、非敏感样本做影子报价；
- 至少 2 个客户愿意在达到价格/质量门槛后进入付费试点；
- 至少 1 个合法供应源可完成端到端真实账单核对。

### 阶段 B：第 15–30 天，供给与单位经济验证

动作：

- 取得首发供给对商业模式、终端用户地区和数据处理的书面确认。
- 用真实任务建立输入/输出/缓存/失败/延迟分布。
- 对官方 Standard、Batch/Flex 与候选市场供给做同口径比较。
- 完成支付、税务、数据和许可证的专项清单。

退出条件：

- 至少一个目标 workload 的 p50 买方节省达到 10%，且 p90 任务贡献利润为正；
- 失败、退款、重试和部分完成纳入压力测试后仍不倒挂；
- 上游账单与平台回执可以逐笔或按日闭合。

### 阶段 C：第 31–60 天，受管闭测

动作：

- 只允许邀请制 B2B 租户、P0/P1 和限额任务。
- 平台运营人员审核每个供应源和 RateCard。
- 记录报价接受率、完成率、账单差异、支持成本和重复使用。
- 不开放供应方现金自助出款；使用合同化结算或 PSP 沙盒。

退出条件：

- 连续 30 天无重复扣费和跨租户内容泄漏；
- 账本不平衡为 0；
- 账单差异率低于合同阈值；
- 至少 3 个试点客户中有 2 个重复使用并愿意付费。

### 阶段 D：第 61–90 天，付费 Beta 决策

只有以下全部成立才进入：

- 公司主体、地区、Provider 授权、许可证、PSP、KYC/KYB、税务与数据结论齐备；
- 多维 RateCard 与买方报价/供应方净报价已实现；
- 至少两个独立合格供应源，或明确接受单供应源产品定位；
- 供应方集中度、故障和对账门禁可运行；
- 付费试点的贡献利润、留存和支持成本达到业务负责人批准的阈值。

若没有第二个合格供应源，不要把产品称为“开放市场”；应继续作为受管推理网关和 FinOps 产品销售。

## 12. 业务负责人必须确认的决策

| 决策 | 推荐默认 | 不确认的后果 |
| --- | --- | --- |
| 首发地区与签约主体 | 一个 Provider 明确支持的地区；中国大陆单独立项 | 无法决定 Provider、币种、支付、税务与数据路径 |
| 首发 ICP | B2B 异步 P0/P1 | 产品和销售无法聚焦 |
| 首发 workload | 抽取/分类/摘要/评测四选一 | 无法形成可比成本和 SLA |
| 供给范围 | S0 + S1；S4 默认关闭 | 授权与供给质量不可控 |
| 价格模型 | Spot 节省分享；其他成本加透明平台费 | 12% 抽成与供应报价继续冲突 |
| 最低节省/贡献门槛 | 先以 10% 节省、任务贡献为正做试验 | 无法做报价准入 |
| 数据范围 | 只 P0/P1 | P2/P3 会提前放大合规和安全成本 |
| 产品命名 | Beta 前称“授权推理容量/FinOps”，不强调个人共享 | 容易制造违规供给和错误用户预期 |
| 许可证 | 商业发布前补齐 | 不能安全分发或商业部署 |

## 13. Go / Pivot / Stop

### Go

- 买方愿意为成本治理、执行证据和统一结算付费；
- 至少一个工作负载存在可持续、可授权的成本优势；
- 可以取得两个以上独立合格供应源；
- 贡献利润在真实失败和支持成本后仍为正。

### Pivot

- 若低价供给不足但企业愿意为治理付费：转为 BYOC 多模型 FinOps/SaaS。
- 若只有自托管模型形成折扣：转为开源模型容量交易与托管平台。
- 若只有文件异步任务有明显价值：聚焦“可验证批量 AI 作业平台”。
- 若只有单一 Provider：作为该 Provider 的受管批量网关，而不是市场。

### Stop

- 无法取得任何 Provider 对商业模式和地区的书面许可；
- 折扣完全依赖个人订阅、积分或共享账号；
- 买方价格不能低于官方 Batch/Flex，且客户也不愿为治理付费；
- 真实支付、税务、KYC/KYB 和出款路径不可行；
- 单位经济需要靠无限增长或挪用供应方应付才能成立。
